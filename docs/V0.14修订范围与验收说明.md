# V0.14 修订范围与验收说明

## 1 本次修订的边界

本次依据《V0.14 增量实现方案与验收标准》修订 2，改造原 V0.14 引入的任务与双 Agent 原子换币能力，并保留之后 V0.15 新增的服务购买实现。发行标签采用 V0.15.1 规范修订预览版，验收状态为 NOT_FULLY_ACCEPTED，避免覆盖或倒退已有版本。

文档方案所列 AT-01 至 AT-36 是完整验收范围，不代表本次已有相同数量的通过结果。当前实现与随包报告应分开阅读：源码中出现一个接口或一次正常运行，不能替代对应测试的所有前置条件、故障注入和证据要求。

## 3 与完整标准的差异必须显式记录

新任务中心中的旧五模板当前为脚本适配；它们的模型模式仍从原单 Agent 页面使用。不能将这一状态表述为五类旧模型任务均已完成独立进程迁移。

Agent 配置的创建和身份安装由 GUI/API 完成，之后可以通过 `start-agent-a.cmd`、`start-agent-b.cmd` 或独立终端运行 worker。仅运行 `agent-worker --init` 不能代替完整注册流程。钱包秘密与模型配置分别保存为 `wallet-secret.json`、`model-secret.json`，控制端不读取钱包秘密。

V2 管理员身份与旧 health CSRF 分开。`open-task-center.cmd` 读取本实例的 `control-admin.token` 并打开片段初始化入口，页面清除片段后通过 HttpOnly 会话访问 TaskCenter API；Agent Bearer 不具有全量执行及导出管理权限。脚本还核对构建与数据目录，避免误开其他实例。

控制服务内部网关已经承担交易意图、签名核验、哈希持久化、广播与对账职责。实际 HTTP 路由也已实现：Agent 使用 `POST /api/v2/tx-intents` 取得其已准备意图的 unsigned 内容，使用 `POST /api/v2/tx-intents/<intentId>/submit` 提交签名，`GET /api/v2/tx-intents` 仅列出自身意图。prepare 不是额外的 `/prepare` 路径；submit 验证通过不等于广播成功。准确字段见 `docs/control-api_V0.15.1.md`。随包已提供 balance、transfer、approve、swap、swap_deposit、peer_swap 六类 `tasks/<taskType>/1.0.0/` 版本包，包含 manifest、input schema、任务定义、UI schema、角色提示词与默认 fixture。

方案中拟议的所有 HTTP 路由及插件安装接口，仍需按最终实际接口与文件清单逐项核对。不能把内部方法的存在等同于公共 API 契约已完整实现，也不能把任务资料包理解为可执行任意 JavaScript 的插件。

任务中心已采用 SVG 三泳道图，按 Execution 的角色绑定与 Agent 身份布局，绘制记录中实际存在的边，并支持点击节点和连线查看原始事件及负载。图 JSON、GraphML、节点 CSV 和关系 CSV 可分别下载。页面绘图仍不能替代 AT-26 对来源、边两端及多种格式数量一致性的独立检查；缺少端点时不补造连线。

固定提交 `cc51b37456eaec19ffcd002e07a33d8466fdff28` 的基线材料已保存至 `vendor/legacy-source/`。逐项对照 `vendor/v013-build-info.json` 的结果为 42 个受跟踪文件哈希匹配，其中 12 个为原始 TypeScript 源文件；不是 42 个 TS 文件。核验记录见 `docs/source-baseline-verification.json`。新增控制运行时当前为可执行 ESM；`pnpm typecheck` 使用 `tsconfig.control.json`，只严格检查 `src/control/types.ts` 和对应类型测试，不把运行时 ESM 纳入类型检查。完整 TS 运行时迁移、冻结依赖安装、第三方干净全源码构建与最终包一致性仍需单列 AT-01 证据，不能只依据运行成功或接口类型检查通过推导。

## 4 如何判定验收结果

先核对每份 `acceptance-summary.json` 的 buildHash 与交付 `build-info.json.sourceHash`，再读取其逐项结果。目录名含 acceptance 不代表来自最终构建，单项重测不能与另一构建的 core 结果拼成全通过。最终修补轮次的复测入口为 `docs/acceptance-final-core-r3/`、`docs/acceptance-final-recovery-r3/` 和 `docs/acceptance-final-stability-r3/`；未实际生成报告时仍缺该轮证据，不预填通过数或哈希。较早 final/r2 报告不能代替 r3。现有材料的范围和历史关系见 `docs/验收证据索引_V0.15.1.md`。相应 CSV、机器信息、执行 ID 和证据文件应互相定位。单用例或 core 运行产生的未测试项目应保留待测或 BLOCKED，不能把默认填充项算作通过。没有匹配最终构建的复测时，该项目仍缺最新证据。

判为 PASS 必须覆盖该用例写明的全部必需子条件。若只覆盖正常分支，或缺少某个平台、截图、链上回执、注入点与独立核验，应记录实际已覆盖部分和缺口。FAIL 修复后的复测必须留下新的证据，不以修改报告状态代替复测。

以下条件目前需要外部资源或人员配合：

- AT-01 尚未完成完整 TS 运行时与第三方干净全源码构建验收；严格接口类型检查不能替代。
- AT-22、AT-23、AT-24 等恢复条目中未执行的 Agent 崩溃点、事件归档/ACK 崩溃点、链身份变化及记录失败注入，仍按实际报告保留缺口。
- AT-32 需要可用真实模型凭据、固定服务版本和 10 次完整尝试；本地协议夹具不能替代。
- AT-31、AT-34 的 GUI 验收因 ComputerUse 无法可靠识别和确认 URL，明确保留 BLOCKED；静态 DOM 或 API 检查不能代替浏览器交互、双尺寸和干净用户实测。
- AT-35 需要 Apple Silicon macOS 实机与对应原生发布包；Windows 或 CI 结果不能代替。
- AT-36 需要未参与主要编码的独立核验者按手册操作并签字；自动化脚本不能代签。

这些条件缺失时应标 BLOCKED。其他实现或测试缺口也必须如实保留。只有完整必测项均通过、资金与证据类发布阻断项清零后，才能称为本范围正式验收通过；当前预览标识不作这一承诺。

## 5 资金与恢复的解释口径

Execution 的运行状态、业务结果与资金结果分别解释。完成、停止或 Agent 自述成功，不等于链上订单已成交或托管已归零。

停止后若有 Open 订单、Pending/Unknown 交易、未记录的参与钱包交易或记录失败，应保留待处理状态和环境锁。退款必须有明确取消或到期清退交易及回执。到期不会自动退款，恢复也不能通过改 nonce 或换 salt 重付。

控制端重启时先核对存活原链、恢复持久状态、补写归档并对账，再允许恢复工具。旧租约应被拒绝。具体崩溃点是否已通过，只由对应 AT 用例结果证明；不要把正常重启演示扩大为任意故障下无损续跑。

## 6 V0.15 保留检查

`docs/v015-protected-baseline.json` 记录 11 个服务购买相关文件的原始哈希，涵盖服务核心、Provider/Evaluator 流程、服务注册、相关共享场景模块、界面和服务托管合约。本次逐文件重新核对，11 个文件全部与保护清单一致；没有改动 V0.15 受保护实现。`runtime\node.exe dist\cli.mjs doctor` 会输出逐文件比对及 `serviceV015Unchanged`。

文件级一致性证明这些受保护文件没有变化，不能单独证明新增控制模块与整包运行没有兼容问题。因此仍需运行服务购买回归，覆盖正常付款、错误报告、错误批准、Evaluator 离线、超时退款和旧入口兼容。服务购买不因本次修订而改称独立进程新实现。

## 7 交付与复核

交付应包含运行包、当前源码与固定基线来源、依赖锁、版本与哈希清单、任务/Agent 操作手册、API 和数据说明、逐项验收表及实际证据。未提供的平台运行包或实机证据必须明确列为缺失。`scripts/package-v014.py` 输出 V0.15.1、NOT_FULLY_ACCEPTED 的发布清单，排除 data* 运行目录、build 诊断目录、tools、node_modules 和凭据文件；这些运行数据不能随发行包分发。`scripts/compile-peer.mjs` 只从显式 `SOLC_JS_PATH` 或已安装的 solc 0.8.30 加载编译器，不依赖私有 tools 目录。

第三方复核可先运行 doctor，再按“只发布任务 → 分别上线 Agent → 分配角色 → 正常换币 → 暂停与资金收尾 → 离线检查”的顺序执行。最后核对完整标准中尚未通过或 BLOCKED 的项目，而不是只重演一条正常链路。
