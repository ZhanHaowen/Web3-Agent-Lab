# V0.18.3 更新说明

日期：2026-11-23。基于 V0.18.2（提交 `333ffb8611386a7690348e86910da8427cd5edba`）增量修改。本次源码发布包含代码、版本说明、测试报告与公开测试摘要；没有制作新的 EXE 安装包或 Windows 便携运行包。GitHub 自动生成的 Source code ZIP 是源码归档，不包含便携运行时和已安装依赖。

本版处理双 Agent 报价交易中的两个问题：交易尚未确认或结果不明时，怎样恢复而不产生第二次付款；报价已被接受后，怎样确保授权、挂单和成交仍然遵守原条款。直接覆盖原工作台 `/api/scenarios` 和独立 Agent 的 `/api/v2/executions` 两条 `peer_swap` 执行路径。

发布前 Windows 本地回归为 26/26 阶段通过，其中单元 317/317、旧版 TypeScript 145/145；另有真实本地链专项 13/13、预算约束 23/23 和 BNB SDK 离线冒烟通过。这些数量不是同一统计层级，不合并相加。历史 AT-15 仍为部分覆盖；本轮没有真实 LLM、公网写交易或 macOS 真机验收。结果与限制见[测试报告](V0.18.3-TEST-REPORT.md)，可下载的摘要和原件校验信息见[公开证据索引](test-results/v0.18.3-publication/README.md)。GitHub 独立 Windows 验证也已完成，下载报告与本地源码摘要一致，见[发布验证记录](releases/V0.18.3-publication-validation.md)。

## 1. 交易结果与业务动作分开管理

- **等待确认：** 保存交易意图、签名交易哈希、nonce 和所属业务操作；不推进依赖它的授权、挂单或成交。短轮询结束后仍有后台监视器核对原交易，等待时间不会被解释为“交易失败”。
- **链上成功：** 取得成功回执后，再核验授权事件、订单条款或订单终态。业务后置条件满足后才允许推进下一阶段。脚本阶段不再在发出交易之前提前递增。
- **链上回滚：** 保留失败回执和原因，进入需要处理的状态，禁止自动重签并重试授权、挂单或成交。已开放的订单仍允许明确的取消或到期清理。
- **结果未知：** 保留原交易和资金状态，继续查询。RPC 报错、缓存缺失、nonce 冲突都不会被当作“可以重新付款”的证据。
- **停止实验：** 停止后续业务行动，但继续核对已经发出的交易。挂单在停止后才确认时，仍恢复订单编号并识别托管资产；资金未处理完，不释放实验环境锁。
- **进程恢复：** 独立 Agent 模式恢复持久化意图和链状态；需要明确 resume 才恢复执行。广播前故障的恢复只允许重发原签名字节，保持同一哈希和 nonce，不生成另一笔授权。

业务操作以 `operationId` 识别，不依赖模型又生成了哪个工具调用编号。同一报价下重复提出同一授权、挂单或成交时复用已有记录；改变参数会被拒绝。

原始签名交易仅作为运行时恢复材料加密保存在本地私有目录，不进入可导出的实验包。私钥与 API Key 仍按原有采集规则处理。

## 2. 失败后的资金清理

“实验停止”与“资金已清理”分别记录。订单仍开放时，界面提示取消订单或等待到期清理，原环境保持占用。

执行结束、资金结局与任务检查也分别记录。退款完成可以封存实验，但原兑换任务仍属于未成交，不能把 `completed` 或退款成功解释为兑换任务成功。

取消或到期清理如果真实回滚，后续明确的人工操作可以发起关联的新 attempt，条件是重新取得旧回滚回执并确认旧 nonce 已消耗。新记录保留同一个 `operationId`，以及 `priorIntentId`、`priorReceiptHash`、`cleanupControlId`。相同控制请求不会生成多个 attempt。

这项权限只适用于 `cancelOrder` 和 `expireOrder`，不会开放 Agent 自动重试成交。清理期间取得执行级控制互斥，后台监视器及另一控制请求不会抢占。Worker 重新上线后，继续执行或直接清理都不再被过时的离线错误阻塞；历史错误事件保留。

## 3. 已接受报价成为固定执行依据

报价生成时保存完整条款：报价 ID 和版本、双方角色与地址、TokenA/TokenB、买卖数量及最小单位、到期时间、salt、订单 ID、条款哈希，以及执行编号、链实例、合约地址、会话范围和合约代码哈希。

接受报价时生成固定的 `acceptanceId` 与接受快照。先校验消息接收人、报价引用、可见报价、消息额度及字段，再提交接受状态。接受消息可附备注或正确的条款哈希，但不能夹带新的交易数量或收款方。

- 接受后再次改价或替换报价会被拒绝。
- 模型决策生成时即绑定报价版本和接受编号，排队中的旧工具调用不会在执行时悄悄改绑新报价。
- 交易工具从已接受快照构造参数；模型额外提供金额、地址等不在工具定义中的字段会在签名前被拒绝。
- 金额按现有实验代币的 6 位精度统一转换。新发出的授权金额采用报价数量；已有 allowance 足够时仍允许复用，不主动把历史授权收紧为报价金额。
- 独立检查器核对接受快照、交易归属、实际参数、回执和链上效果。不能只凭 Agent 的“成功”回答判定通过。

当前保证建立在可信平台控制服务与现有实验合约上。报价哈希用于绑定和核验，不等于新增了链上的双方报价签名协议；独立 Worker 仍按既有交易描述符签名检查规则工作。

## 4. 记录失败与重复请求

独立进程路径中，接受事件和接受状态使用 SQLite 事务提交。数据库提交失败时，内存状态、事件引用和数据库状态一起回滚；数据库已提交而文件导出失败时，保留接受事实，明确返回 `recorded_export_pending`，暂停进一步业务处理。

消息使用稳定请求编号去重。相同请求恢复时复用原消息、报价 ID、salt 和版本，不再次消耗消息额度；相同编号但内容不同会被拒绝。

交易已经提交后发生响应错误时，错误记录保留交易哈希、意图和状态，不再笼统标记 `submitted:false`。原始失败证据和后续恢复证据均保留。

## 5. GUI 与导出变化

- 原工作台显示当前失败原因、资金状态、接受编号及预期订单编号。
- 待确认、需要处理与开放托管状态有明确提示；恢复与清理仍调用服务器端同一套校验。
- 导出的原始事件增加报价接受、交易业务核验、失败及恢复记录。
- 派生图增加报价到接受快照、接受快照到交易意图的关联，保留原事件引用。
- 旧数据缺少接受绑定证据时明确标记 `legacy_unverified` 或关系缺失，不补造旧记录。

## 6. 对原有功能的影响

保留单 Agent 五类任务、独立 Agent、服务购买、预算实验、API/本地模型入口、采购支付研究、测试网配置与独立 BNB SDK 模块。没有新增外部依赖，也没有改变实验合约接口。

本次新机制的直接适用对象是 `peer_swap`；不能据此认定其他支付协议或公共测试网都新增了相同恢复保证。其他模块按原有测试做兼容回归，实际结果和未覆盖范围见 [V0.18.3 测试报告](V0.18.3-TEST-REPORT.md)。

旧入口新建任务与旧实验包查看继续保留；**缺少接受快照的旧版未完结执行，不作为本版可直接接管的迁移对象**。切换版本前应在原版本处理完 pending 和开放托管订单，保留原始数据备份。本次在独立副本中验证，没有替换已有安装的数据目录，也没有为旧任务补造接受证据。

## 7. 本地核验操作

1. 按仓库 README 的源码步骤准备 V0.18.3 依赖与运行时，构建后运行 `start.cmd`，核对页面和健康接口版本为 V0.18.3；不要把旧桌面 EXE 的运行结果当作本版结果。
2. 创建双 Agent 报价交易，关闭自动出块，逐笔确认卖方授权、挂单、买方授权、成交。等待期间多次单步不应增加交易数量。
3. 在挂单等待确认时停止，再出块。应看到开放订单和托管资金，环境仍占用；明确取消并确认退款后才释放。
4. 接受报价后尝试改变数量，检查拒绝事件及“没有新增对应交易”的证据；正常流程仍应按原报价完成。
5. 导出实验包，核对原始事件、接受快照、交易哈希/回执、检查结果及溯源图。具体已执行的自动化用例和证据路径见测试报告。

不要用删除数据库、重置链或新建一次支付来处理仍然未知的旧交易。应先恢复 RPC/Worker/记录服务，再核对原意图；未取得可靠证据的状态继续保留为未解决。
